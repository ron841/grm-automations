## Q3 — Human-AI loop observations

### Lead observation

**The relay pattern (Opus drafts → Ron pastes → Code executes → Ron relays results) worked well when Opus's drafts were specific and verifiable, and worked poorly when Opus assumed state that Code could see but Opus couldn't.** The read-only recon steps (prompts #30, #31, #34) were the highest-leverage parts of the day because they converted Opus's assumed state into Code-verified state before editing began.

### a) Where the relay worked best vs. created friction

**Best:**

- **Grandview Phase 1 handoff → Ron's palette override (prompts #25 → #27).** Opus supplied the build plan, Code ran Phase 1 (node-vibrant extraction), Ron caught that the deterministic mapping would put gold-as-primary instead of green, and injected the swap *before* Phase 2. This is the cleanest example of three-way collaboration: automation does the work, human catches the semantic error, drafting layer reincorporates.
- **v0.7.3 three-batch authoring (prompts #35, #36, #37, #38).** Each batch was a complete self-contained spec with verifiable SHAs ("Verified SHAs to reference..."). Opus's drafts had enough state anchoring that Code could verify before editing. The `f302d49`, `13b4189`, `074e936` prefix in Batch C2 is what makes the relay resilient.

**Friction:**

- **Pre-preservation commit labeling (prompt #32 → first execution attempt).** Opus's spec said "v0.7.2 baseline — preservation commit." Code saw that the working tree already had three uncommitted changes (two with today's dates in LESSONS.md) plus the repo already had a `98569ee` v0.7.2 baseline commit. Misalignment: Opus thought we were starting from pristine; Code saw we were mid-session. I flagged before committing; Ron then supplied the A+B split which resolved cleanly. Cost: one round-trip, no damage.
- **v0.7.3-spec.md currency (prompt #30 → recon → prompt #34).** Opus referenced the April 13 spec as if it might still be relevant. Code's recon showed the spec had been fully implemented and reverted. Ron responded with "the v0.7.3 you're now drafting is a fresh spec." Without that recon layer, the relay would have produced a merge of old-spec + new-findings that could have re-implemented rejected rules.

### b) Drafting layer vs. execution layer state divergence

Three concrete examples from today's transcript:

1. **Batch A commit #2 head template assumption.** Opus's spec: "find the section that specifies what belongs in `<head>`." Code's reality: no such section. Opus assumed the structure existed based on analogous content in other skills; Code had to report "no head template found, skipping step 4."

2. **v0.7.3-spec.md status assumption.** Opus's spec referenced v0.7.3-spec.md as "the draft that already exists" — truthful but incomplete. Code's git-log showed the seven rules in the spec had been committed and then reverted. Opus and Code had the same *file contents* but different *interpretations of file state*.

3. **Phase 6 check number collision (caught in recon, before authoring).** Opus's spec (v0.7.3-spec.md, April 13) had "Rule 6: OG image entropy gate = Phase 6 check #18." Code's recon showed Phase 6 check #18 had already shipped as "Social metadata completeness." If Opus had authored v0.7.3 without the recon step, commit #6 would have been "add check #18 (OG entropy)," silently overwriting the already-shipped check #18.

### c) Three-batch split vs. one big paste

**Evidence that batching helped:**

- Batch C1 pre-flight was scoped specifically to "verify the count claim from Batch B." If Batches B and C1 had been one paste, the recursion (verify my own previous claim) would have been absent from the spec.
- Each batch produced its own `git log --oneline -N` report and SHA set. The Batch B → C1 handoff spec included "Verified SHAs to reference" with the exact commit SHAs from the prior batch. This is a form of typed handoff between stages that wouldn't exist in a monolithic spec.
- Batch C2 arriving truncated was caught *because* it was a fresh message with a clear start. In a continuous stream, the truncation might have looked like a transition into freeform prose rather than a breakage.

**Evidence that batching was overhead:**

- Batch B's commits were similar enough in shape (each: edit SKILL.md, add new check, bump count) that bundling them would not have meaningfully raised risk. The per-commit reports took ~20% of the batch time.
- Some of the pre-edit verification steps (commit #3 "confirm Corporate jargon section exists") were sanity checks that would have been equally valid as inline verification inside a combined spec.

**Net: batching paid off clearly in Batches A → B → C1 transitions (where each batch needed to reference the prior batch's SHAs) and was pure overhead within a batch.** The right split is probably by *dependency on prior state*, not by commit count.
