# Photo Capture Standard

The contract the audit skill applies when pulling photos across surfaces. This doc is read by the audit-skill scripts and by anyone debugging a photo-capture failure.

## Surface order

Capture from these surfaces in order. Stop when the cap is reached or each surface is exhausted.

1. **Google Places Photo API.** Cap is 10 photos per place_id. Pull all 10 if available at native resolution. This is the highest-trust surface (Google's curated set).
2. **Facebook cover photo.** Single highest-priority single asset. Captured first when the FB page is reachable. Cover photo at full hi-res via Playwright DOM extraction past the login modal.
3. **Facebook page photos grid.** Scroll-load until grid stops appending or 50 photos captured. The login wall does not block the photos grid for public pages.
4. **Instagram photos.** Only when the IG handle is verified in Phase 4. Pull recent N posts via Playwright. Out of scope for v0.1 if the skill cannot reach IG without auth.
5. **Operator-supplied.** Slot for photos the operator emails or hands over. Not captured by the skill; the slot exists in the workspace for downstream insertion.

## Native resolution

Always pull at native resolution. The Places Photo API request uses `maxHeightPx=4800&maxWidthPx=4800` to force the largest available size; smaller images downscale automatically. The build pass downscales for delivery; the audit captures the original.

Hand-cropped or operator-supplied photos may not reach 4800px. That is fine; the build pass works with whatever native size the source provides.

## Cap

Ten photos per place_id at the Places Photo API. The cap is a Google constraint, not a GRM rule. Surface this in the intake §10 capture status: "GBP photos: 10 captured (Places API cap)."

Total photo count across all surfaces is not capped. A prospect with 10 GBP photos plus 1 FB cover plus 12 FB page photos plus 6 IG photos lands at 29 total. The build pass selects per-slot from the full library.

## Owner-first ordering

Photos with `authorAttributions[].displayName` matching the business name (case-insensitive, ignoring punctuation and entity suffix) are tagged `provenance: owner-uploaded`. Photos with author attributions naming a person are tagged `provenance: customer-uploaded` and the reviewer name is preserved in metadata.

When writing filenames, owner-uploaded photos sort first (`01-gbp-owner-{slug}.jpg` through `08-gbp-owner-{slug}.jpg`), customer-attributed photos sort after (`09-gbp-customer-{slug}.jpg`, `10-gbp-customer-{slug}.jpg`).

The reasoning: customer-attributed photos rank higher than owner-uploaded for downstream slot assignment (a customer photographing the work at the property is stronger evidence than an operator-curated promo shot), but owner-uploaded photos are typically more numerous and form the bulk of the library. Sorting owner-first by index is a deterministic ordering choice; the per-slot selection at synthesis time uses the metadata, not the filename.

## Filename convention

```
NN-{source}-{provenance}-{slug}.{ext}
```

Where:
- `NN` is a zero-padded two-digit index, owner-uploaded first then customer-attributed.
- `source` is `gbp`, `fb-cover`, `fb-page`, `ig`, or `operator`.
- `provenance` is `owner` or `customer`.
- `slug` is the prospect slug (kebab-case business name).
- `ext` is `jpg` or `png` per the source.

Examples:
- `01-gbp-owner-yankee-handyman.jpg`
- `09-gbp-customer-yankee-handyman.jpg`
- `fb-cover-yankee-handyman.jpg`
- `fb-page-photo-03-yankee-handyman.jpg`

The FB cover photo and page photos do not carry the `NN` prefix because they have only one surface-canonical instance each.

## images/README.md format

Generated by Phase 2 of the audit. One row per photo:

```markdown
# Photo Catalogue

| File | Source | Provenance | Author | Width x Height | Notes |
| --- | --- | --- | --- | --- | --- |
| 01-gbp-owner-yankee-handyman.jpg | GBP API | owner | THE YANKEE HANDYMAN LLC. | 3024 x 4032 | |
| 02-gbp-owner-yankee-handyman.jpg | GBP API | owner | THE YANKEE HANDYMAN LLC. | 4032 x 3024 | |
| 09-gbp-customer-yankee-handyman.jpg | GBP API | customer | Diane Bennett | 3024 x 4032 | reviewer cross-ref to review #12 |
| fb-cover-yankee-handyman.jpg | FB cover | owner | (FB page) | 1320 x 976 | |
| fb-page-photo-01-yankee-handyman.jpg | FB page | owner | (FB page) | 1080 x 720 | |
```

Customer-attributed photos that cross-reference a captured review carry the reviewer name AND the review index in the Notes column. This cross-reference is what synthesis uses for the customer-photo-plus-customer-review pairing pattern.

## Failure modes and tagging

| Failure | Tag |
|---|---|
| Places API quota exceeded mid-Phase-2 | `[scrape-failed]` on remaining photos, retry next run |
| Photo URL returns 4xx | `[scrape-failed]` per-photo, log to process-notes |
| `authorAttributions` field missing | `provenance: unknown` plus `[low-confidence]` flag |
| FB page exists but cover photo absent | `[gap]` (operator chose not to set a cover) |
| FB page does not exist | `[gap]` for all FB photo fields, NOT `[scrape-failed]` |
| FB Playwright login modal blocks photos grid | `[scrape-failed]` only after retry; the panel typically loads on retry |

## What this doc does not specify

- Per-slot selection (which photo goes in hero, which in section 3, etc.). Synthesis owns that.
- Image optimization (WebP conversion, sizing for build, lazy-load). Build owns that.
- Photo-subject tagging beyond cross-reference. Vision tagging is v0.2.
- OG image generation. Build owns that.
